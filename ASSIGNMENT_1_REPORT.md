# Full Stack Development with Next.js: Assignment 1 Technical Report

## 1. React Server Components (RSC) vs. Client Components

### 1.1 Architecture & Strategy in CodeSpace
In the CodeSpace architecture, we adhered strictly to the Next.js App Router paradigm, dividing our component tree into React Server Components (RSC) and Client Components based on their necessity for interactivity and browser APIs.

**React Server Components (RSCs)** were used as the default for all layouts (`layout.tsx`) and pages (`page.tsx`). By doing so, we shifted the heavy lifting of data fetching, routing, and static HTML generation to the server. For instance, the main dashboard (`src/app/(dashboard)/page.tsx`) acts as a pure Server Component. It securely connects directly to our Prisma database via `prisma.project.findMany()`, bypassing the need for an intermediary REST API. This reduces the JavaScript bundle size sent to the client, prevents waterfall data fetching, and secures our database credentials.

**Client Components** (denoted by the `"use client"` directive) were pushed to the leaves of the component tree. We restricted their use to components that require:
- Browser APIs (e.g., `localStorage` for our Zustand store, `window` for viewport calculations).
- Interactivity (e.g., `onClick` handlers, form submissions via `react-hook-form`).
- State and Lifecycle hooks (`useState`, `useEffect`, `useOptimistic`).

Examples of Client Components in CodeSpace include `ProjectList.tsx`, `LoginForm.tsx`, and the Sidebar controls. By isolating them, the majority of the application remains static and highly performant.

## 2. Hydration & Mismatch Mitigation

### 2.1 The Hydration Challenge
Hydration is the process by which React attaches event listeners and state to the static HTML generated by the server. A "hydration mismatch" occurs when the server-rendered HTML differs from the HTML React expects to render on the client (e.g., when rendering UI based on a user's local `localStorage` theme preference).

### 2.2 Mitigation Strategies Used
To prevent hydration errors in CodeSpace, we utilized two primary strategies:
1. **Suppression for Safe Attributes**: For attributes like `class` injected by `next-themes` (which reads from `localStorage`), we applied `suppressHydrationWarning` to the `<html>` tag in `src/app/layout.tsx`. This tells Next.js to ignore the mismatch safely, as the client will immediately inject the correct theme class without a jarring layout shift.
2. **Hydration Hooks for Zustand**: To safely read from our persisted Zustand store (`useWorkspaceStore`), we implemented a custom `useStoreHydration` hook. This hook defaults to a neutral state during the server-render and only populates the local state (`compactMode`, `projectFilter`) after the component has mounted on the client (`useEffect`). This ensures the server and client initial HTML are perfectly aligned, preventing fatal React errors.

## 3. Zustand vs. Server-State Libraries

### 3.1 Purpose of Zustand
In CodeSpace, we selected **Zustand** specifically for managing **ephemeral, client-side UI state**. Zustand is exceptionally lightweight, boilerplate-free, and handles local persistence gracefully via its `persist` middleware. We used it to track:
- `sidebarCollapsed` (boolean)
- `compactMode` (boolean)
- `projectFilter` (active/completed)

### 3.2 Comparison with Server-State (React Query/SWR)
Unlike Redux or Context API which often become monolithic, Zustand was kept strictly to UI preferences. We deliberately did **not** use Zustand to store server data (like the list of Projects or Tasks). 

Instead, server-state was managed directly by **Next.js Server Components and Server Actions**. 
- **Data Fetching**: Handled by RSCs fetching from Prisma.
- **Data Mutation**: Handled by Server Actions (`createProject`, `toggleTaskStatus`), which automatically call `revalidatePath("/")` to update the UI.
- **Optimistic UI**: Handled via React 18's `useOptimistic` hook (seen in `TaskList.tsx`), providing instant feedback without requiring a heavy global state manager like React Query or SWR.

This hybrid approach allows us to enjoy the instant mutations of optimistic UI while keeping the source of truth firmly on the server, avoiding the notorious "stale data" problem of traditional global state managers.

### 4.2 Optimization Implementation
`ProjectList.tsx` and `TaskList.tsx` dynamically import their heavy Dialog
forms (`CreateProjectForm`, `CreateTaskForm` — which pull in `react-hook-form`
and `zod`) via `next/dynamic(..., { ssr: false })`, so that validation-library
JavaScript is only fetched and evaluated once a user opens the "New Project"/
"New Task" dialog rather than on initial page load. This pattern is in place
and is architecturally sound, but a rigorous isolated before/after
measurement of its effect was not part of this audit (see the "Not
independently re-verified" note in `PERFORMANCE.md`).

During this audit, one real accessibility issue was found and fixed on the
actual dashboard (not present in the earlier, mistargeted audit): the
`--muted-foreground` and `--destructive` design tokens used on plain white
backgrounds fell just under the WCAG AA 4.5:1 contrast threshold. Both were
darkened one shade in `globals.css`, bringing the dashboard's accessibility
score to a verified 100/100.
